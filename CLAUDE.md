# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Quick start

```bash
docker-compose up -d
```

Then visit `http://localhost:80`. The `docker-compose.yml` spins up MySQL 8.0 and an Apache2+PHP 7.4 container. The SQL schema is auto-loaded from `LMS_DB_SETUP.sql` on first run.

No build step, no package manager — this is a traditional LAMP application.

## Tech stack

- **Backend**: PHP 7.4 with MySQLi (procedural style), no framework. Session-based auth with bcrypt password hashing.
- **Frontend**: Vanilla JS SPA with jQuery 3.7.1 for AJAX. No bundler, no npm.
- **Database**: MySQL 8.0 (`LMS_DB` schema defined in `LMS_DB_SETUP.sql`)

## Architecture

### PHP backend (`php/`)

All PHP endpoints return JSON. Error handling is centralized in `bootstrap.php` — it catches all errors/exceptions and returns `{"status": -99, "msg": "Server error"}` without exposing internals.

| File | Purpose |
|------|---------|
| `php/bootstrap.php` | Global error/exception/shutdown handler, included first by all backend scripts |
| `php/entry_backend.php` | Login and signup (`?request=login|signup`) |
| `php/mainpage_backend.php` | Main API dispatcher — routes `POST oper` + `ctnt` to the appropriate handler functions |
| `php/operations_define.php` | All business-logic functions (CRUD for users, books, borrow/return records, SQL execution, backup list) |
| `php/backup_restore.php` | Database backup/restore/delete via `mysqldump` shell commands |
| `php/logout_backend.php` | Session destroy |
| `php/uname_auth_backend.php` | Returns current session user (username + authority) |

Database credentials live in `private/mysql-conn-config.php` (generated by Dockerfile or created manually — see README).

### Frontend JS (`js/`)

The SPA is loaded via `index.html`. Script load order matters — `index.html` lists them in dependency order.

**Layers (bottom-up):**

1. **`js/api/http_client.js`** — Thin wrappers around `$.ajax` (`apiPost`, `apiGetJson`, `apiPostJson`). All POST data goes as form-encoded JSON.
2. **`js/api/*_api.js`** — Domain API modules (`appApi`, `dashboardApi`, `libraryApi`, `accountApi`, `systemApi`). Each method maps to a `{oper, ctnt, ...}` payload sent to `php/mainpage_backend.php` (or `backup_restore.php` for backup ops).
3. **`js/render/*_renderer.js`** — DOM rendering modules. `tableRenderer` is the shared table builder; the others are domain-specific.
4. **`js/pages/*_page.js`** — Page controllers registered on the global `hori_btn_func` map (keyed by page name). Each function wires up event listeners and calls APIs + renderers.
5. **`js/template_loader.js`** — Fetches HTML `<template>` files from `html/templates/`, injects them into the DOM, and provides `mountPageTemplate()` to swap page content.
6. **`js/page_registry.js`** — Maps page names to template IDs, box IDs, and template file paths (`page_view_config`).
7. **`js/navigation.js`** — Vertical (sidebar groups) and horizontal (page tabs) navigation. Clicking a nav button mounts the corresponding template and invokes its `hori_btn_func` handler.
8. **`js/app_bootstrap.js`** — Entry point. Loads templates, fetches current user via `uname_auth_backend.php`, shows authorized UI elements, initializes navigation.
9. **`js/entry.js`** — Login/signup page logic (used by `html/log_in.html` and `html/sign_up.html`).

### HTML templates (`html/templates/`)

Each page's DOM structure is defined as an HTML `<template>` tag in these files. Templates are loaded at bootstrap and cloned into the `.box` container when a page is navigated to.

### Authority system

Integer-based, stored in `user.authority`:

| Level | Role | Access |
|-------|------|--------|
| 0 | Visitor | Login/signup only |
| 1 | Normal user | Dashboard, search books, borrow/return, view own info |
| 2 | Staff | + User list management, book storage |
| 3 | Admin | + System management (backup/restore) |
| 4 | Root | + SQL execution, restore/delete backups, manage authority levels |

UI elements with `data-auth="N"` are shown only when the user's authority >= N. Backend endpoints enforce the same checks server-side.

### Database schema (`LMS_DB_SETUP.sql`)

- `user` — uuid (PK, date-based like `202605060000`), username, bcrypt password, authority
- `user_info` — card_number, name, phone, email, address (FK to user)
- `book_index` — book_ind (PK), book_name, status (1=available, 0=borrowed), storage_time
- `book_info` — price (FK to book_index)
- `b_r_record` — borrow/return records with is_borrow flag (1=borrow, 0=return)
- `request_rcd` — API request audit log (user_id, IP, timestamp)

### CSS (`css/`)

Modular stylesheets organized by feature area: `mainpage.css` (layout), `entry.css` (login/signup), `navigator.css`, `table.css`, `dash_board.css`, `book_store.css`, `my_info.css`, `loading.css`, `misty-light-windows.css` (theme).

## Common operations

- **Add a new page**: Create a template in `html/templates/`, register it in `page_view_config` (`js/page_registry.js`), add a page controller in `js/pages/`, wire up `hori_btn_func["PageName"]`. Add backend handler in `php/operations_define.php` and route it in `php/mainpage_backend.php` under the appropriate `oper`/`ctnt`.

- **Add a new API endpoint**: Add the function in `php/operations_define.php`, route it in `php/mainpage_backend.php` via `oper` + `ctnt` dispatch. Add the client-side method in the appropriate `js/api/*_api.js` module.

## Important constraints

- PHP uses **procedural style with `mysqli_*` functions** and raw string interpolation for SQL in most places. The few spots using prepared statements are `get_user_list`, `get_book_list`, `get_rcd_list`, `book_store`, and `get_requests_count`. When adding new SQL queries, use prepared statements.
- The `private/` directory is blocked by Apache config and contains `mysql-conn-config.php` and the `backup/` directory. Never expose these via the web server.
- jQuery's `$.ajax` is the HTTP layer — all frontend API calls use it. Don't introduce `fetch` or other HTTP libraries without a deliberate migration.

## No tests or linting

This project has no test suite, no linter config, and no CI. All verification is manual in the browser. Docker-based local deployment is the primary way to test changes.
